ShareX Receipts · A modified ShareX application with an extra save-and-check option

Keep a starting copy alongside each finished capture.

ShareX may apply effects, annotations or compression before saving a capture. This modified version can keep a PNG copy of the image entering that processing, the finished file, and a small record linking the two.

Why you might use it

You prepare an annotated screenshot for a report, then want to inspect the earlier image or check whether a saved result changed later. Keeping just the final JPEG makes that harder. An extra starting copy and processing record give you something concrete to compare.

A concrete example. The test uses an invented image and saves a lower-quality JPEG. The receipt keeps the accepted input pixels separately, so the compressed result does not replace that starting copy. The inspector can then check the stored files against their recorded fingerprints.

1. Enable the extra save

Choose 'Save research receipt' in the supported after-capture tasks.

2. Keep both versions

The app saves the accepted starting image, the result and a record of selected processing information alongside the normal output.

3. Inspect or check later

Open the receipt inspector to compare the files and check whether they still match the saved record.

What this page shows. The screenshots and sample files come from the real modified processing code using an invented image. The browser checker checks saved files; it does not capture your screen.

Where it runs and what is still untested. Here 'starting image' means the image handed into after-capture processing. Edits already made in the region editor are already included. A receipt cannot prove where an image came from or whether its content is true. Normal capture, hotkeys and profile migration still need hands-on validation.

Experimental independent ShareX 21.0.0 fork. Integrity checking does not prove capture authenticity. Original means the accepted WorkerTask input; edits made earlier in a region editor are already included.

03 / The receipt contract

Five files.
Explicit commitments.

The manifest commits exact bytes. Formatting changes count as changes. Canonical pixel identities also detect misleading or inconsistent image commitments.

A sidecar beside the capture connects the task-list entry with the receipt ID and digest. Existing receipts and links are never silently replaced.

05 / Claims that stop at the boundary

Evidence with limits.

What this establishes

The Windows verifier checks supported schema, fixed artifact roles, safe leaf names, byte lengths, SHA-256 commitments, exact directory membership and decoded pixel identities. It rejects linked receipt directories and linked payload files. The original PNG preserves the bitmap accepted by WorkerTask, including any earlier region-editor edits.

What this does not establish

No capture authenticity, trusted timestamp, signature, complete replay, OCR accuracy or upload destination proof is claimed. Requested flags describe intent; observed stages describe actual image states. Only selected settings are recorded at sealing. An attacker who can rewrite the complete bundle can regenerate its adjacent checksum. An independent digest detects such a rewrite. Concurrent filesystem mutation, linked ancestors and hostile image decoder inputs remain outside protection.

What has and has not run

The full modified source fork compiled, then its WorkerTask path processed synthetic pixels and rendered the inspector. Portable executables were exercised separately. Real desktop capture, global hotkeys, normal profile migration, the separate upstream History window, network transfers and every upstream tool were not acceptance-tested. The installed application was not modified.

REA's contribution and source alignment

Existing read-only REA metadata analysis identified ShareX 21.0.0.0 on .NET9. It did not load the CLR, decompile C# or execute ShareX. That supported a public-source route pinned to v21.0.0; version alignment does not prove equivalence with the installed binary. Source inspection identified the actual WorkerTask/file/history integration points. The new implementation and execution evidence came from this project.
